# Как подключить следующий анализатор

Текущая точка расширения — Python-адаптер. Произвольная CLI-программа пока не
становится плагином автоматически: нужно описать её входы, разобрать вывод и
объяснить значения пользователю. Рабочий небольшой пример —
`app/adapters/ffprobe.py`, общий сценарий — `app/core/service.py`.

## Контракт результата

`ToolAdapter.analyze(path)` получает путь к рабочей копии и возвращает
`AdapterResult(findings, tool_runs, artifacts)`:

- `Finding`: категория, исходное имя поля, значение, источник и `location`.
  Источник называет движок, расположение — тег, часть контейнера, поток или объект.
  Одинаковые имена в разных местах сохраняются отдельными фактами.
- `ToolRun`: версия и точные аргументы, времена, код завершения, статус,
  stdout и stderr. Его создаёт `CommandRunner`, которым следует пользоваться
  также для таймаута, отмены и ограниченного захвата вывода.
- `artifacts`: дополнительные JSON-совместимые структуры и пути к производным
  файлам в каталоге рабочей копии. Например, ffprobe сохраняет полное разобранное
  дерево контейнера рядом с нормализованными фактами.

Нулевой код завершения не гарантирует корректный JSON. Адаптер проверяет форму
вывода; ошибка разбора отражается в статусе запуска. Отсутствие программы,
ошибка программы и отсутствие конкретного тега — разные состояния.

## Где подключать

1. Если это новый тип, добавить `FileKind`, правило определения по содержимому
   и запись `PROFILES` в `app/core/formats.py`. MIME и описание области проверки
   не должны обещать больше, чем извлекает профиль. Для нового движка уже
   поддерживаемого типа менять `FileKind` не нужно.
2. Добавить адаптер в `ForensicsService._adapters` и выбрать режимы через
   `_enabled`. Встроенный разбор выполняется всегда; набор внешних проверок
   зависит от быстрого, полного или выбранного режима.
3. Добавить путь/параметры в `AppConfig` и форму `SettingsDialog`, если они нужны.
   `SettingsStore` хранит настройки, демон подхватывает изменения между заданиями.
   Проверку версии добавить в `ForensicsService.check_installation`, назначение —
   в `app/gui/tool_status.py`, пункт выбранного режима — в диалог режимов.
4. Добавить русские названия и пояснения в `app/resources/labels.py`. Общие
   результаты, поиск по проекту, экспертные отметки и экспорт уже работают с
   `Finding`; отдельное окно для каждого нового движка обычно не требуется.
5. Если появились важные для первого взгляда факты, добавить их в карточку
   `app/gui/identity.py`, а короткие пояснения — в `app/analyzers/overview.py`.
   Строки карточки должны открывать конкретный исходный факт. Даты без пояса
   не превращаются в UTC.

Аргументы передаются списком без shell. Обязательные для выбранного парсера
ограничения задаёт сам адаптер: например, ffprobe получает фиксированный demuxer,
доступ только к файловому протоколу и запрет ссылок MOV на внешние данные.
Сетевые запросы и изменение исследуемого файла не входят в контракт анализа.

## Проверка интеграции

Для нового парсера нужны небольшой корректный образец, повреждённый образец и
образец с неоднозначными метаданными. Проверяются исходные значения, расположение,
сохранение повторяющихся полей, поведение при отсутствии утилиты и таймауте.
Для контейнеров отдельно проверяются квоты. Один повреждённый файл не должен
мешать следующему заданию; SHA-256 оригиналов должен оставаться прежним.

После проверки исходников запустите `build.ps1`: он проверяет настоящий
запуск GUI и обработку задания в EXE. Упаковка важна для multiprocessing, Qt DLL
и вспомогательного Python-исполнителя. `scripts/package_preview.py` откажется
архивировать сборку, если Python-файлы приложения изменились после её создания.

Распространение бинарников движка — отдельное решение от поддержки адаптера.
Готовая программа включает закреплённые версии инструментов. При добавлении
компонента обновите перечень зависимостей, лицензий и соответствующих исходников.
